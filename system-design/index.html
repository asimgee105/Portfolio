Server Guide

What each server actually does

“Laravel servers” usually means multiple machines or containers running the same Laravel code behind a load balancer. Other servers have different jobs. Keeping those responsibilities separate makes scaling easier to understand.

HTTPPHP-FPM

Laravel App Server

Runs your Laravel application code. A request reaches Nginx/PHP-FPM, Laravel validates it, checks authentication/policies, executes business logic and returns JSON/HTML. At higher traffic, multiple identical stateless app servers run the same code.

Traffic

Load Balancer

Sits in front of Laravel app servers and spreads incoming requests across healthy instances. It does not replace Laravel; it decides which Laravel server receives each request.

CacheSessionsLocks

Redis Server / Cluster

Stores fast in-memory data such as cache entries, shared sessions, rate-limit counters, distributed locks, queue data and presence information. It prevents every request from hitting MySQL.

SQLDurability

MySQL Primary + Replicas

The primary database accepts authoritative writes. Read replicas copy that data and serve read-heavy endpoints. Replicas increase read capacity but do not remove the need to protect the primary write path.

AsyncLaravel Queue

Queue Worker Servers

Run commands such as php artisan queue:work. They handle email, invoices, image processing, webhooks and reports outside the user request. They can scale separately from web servers.

WebSocketReverb

Realtime / Reverb Servers

Maintain long-lived WebSocket connections for chat, presence and live events. They are different from normal HTTP Laravel servers because thousands of clients may stay connected at the same time.

EdgeStatic

CDN / Edge

Serves static files and cacheable responses close to users. At very large scale it removes traffic from your origin servers before Laravel is even involved.

Observability

Monitoring & Logs

Metrics, logs, traces and alerts show CPU, memory, latency, error rate, queue depth, cache hit rate and slow queries. Those measurements tell you when another server is actually needed.

Important

Server count is not user count

Ten million registered users does not mean ten million concurrent requests. Capacity planning should use peak requests per second, concurrent WebSockets, database transactions and latency targets. The example counts in these pages are learning ranges.

Scaling ladder

One system, four stages

1 userOne Laravel app server and one database. No distributed complexity.
~100 usersUsually still simple. Add indexes, caching or background workers only when measurements show a need.
~1 million usersUse a load balancer, multiple stateless Laravel instances, Redis, workers and read scaling where traffic requires it.
~10 million usersUse larger app pools, stronger failure isolation, replicated/partitioned data where justified, edge caching and serious observability.

Important: scale by traffic, not by a magic number

The architecture diagrams intentionally teach a progression, but real production sizing depends on concurrent traffic. A well-cached Laravel app can serve a very large registered user base with fewer servers, while a write-heavy or realtime system may need more infrastructure with fewer users.
