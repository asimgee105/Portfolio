Case Study 04

POS & Inventory System

A POS has a different scaling priority: checkout and stock writes must stay correct, while product browsing and reports can be optimized independently. This page uses the POS project in my GitHub profile as the practical starting point.

GitHub repository← All case studies

Stage 1 — Transactional monolith

ONE / FEW STORES
Cashier
Laravel POSsales + inventory
MySQLproducts / stock / sales
Receipt / Report

Priority

Sale creation and stock deduction belong in a database transaction so partial checkout does not corrupt inventory.

Bottleneck

Complex dashboard reports can compete with checkout queries on the same database.

First optimization

Indexes, pagination and cached product/catalog reads usually help before adding more infrastructure.

Stage 2 — Cache reads, queue side effects

~1K USERS / MULTI-STORE
Stores
Load Balancer
Laravel x2
Rediscatalog / sessions
MySQL Primary
Queue Workersemail / reports

Checkout stays strict

Inventory mutation remains on the primary database; cache is used for safe read-heavy data such as product details.

Concurrency

Row locks or optimistic checks prevent two terminals from selling the final unit at the same time.

Reporting

Move expensive exports and summaries to background jobs rather than holding cashier requests open.

Stage 3 — Separate operational and analytical load

~100K USERS / LARGE NETWORK
Store Clients
API Gateway
POS API Pool
Transactional DBsales / inventory
Event / Queue
Reporting Storeanalytics / BI

Isolation

Checkout traffic no longer competes directly with historical reports and business analytics.

Multi-store design

Store IDs, inventory location keys and idempotent sale requests become essential as terminals and retries increase.

Offline option

For unreliable store connectivity, a local queue/sync strategy can be introduced with conflict rules rather than making checkout depend on constant WAN access.
