Case Study 02

Laravel URL Shortener

The real project includes short URL creation, redirects, a visit event and a listener that increments click counts. That makes it a useful read-heavy system design example: redirects must stay fast while analytics can happen asynchronously.

Stage 1 — Direct database lookup

LOW TRAFFIC
Browser/abc123
Laravel RedirectResolve short code
MySQLshort_urls

Simple first

One indexed lookup by short code is enough for modest traffic.

Problem

Every redirect hitting MySQL wastes work when the same popular links are repeatedly requested.

Existing event idea

Visit counting should not slow the redirect path; publish an event and update analytics outside the critical request.

Stage 2 — Cache the hot path

Laravel
Redis Cachecode → URL

Big win

Popular redirects become memory lookups instead of repeated database reads.

Analytics

Clicks can be queued or buffered, reducing write pressure on the redirect request.

Safety

Use expiration and cache invalidation when a destination is edited or disabled.

Read-heavy design

Keep redirect serving separate from analytics processing so a reporting spike cannot break link resolution.

Key design

Short codes need uniqueness, compact storage and predictable lookup performance.

At very large scale

Partition by hash/range only when a single database can no longer sustain the write or storage requirement.
